## Event Contract

Allowed events:

- `session_start`
- `recommendation_shown`
- `recommendation_refresh`
- `menu_card_open`
- `map_open`
- `share_recommendation`
- `recommendation_error`

Allowed source contexts are `discovery`, `personalized`, `shared_pick`, and `search`. Allowed share methods are `web_share` and `clipboard`. Allowed error codes are `insufficient_candidates`, `invalid_result`, `data_unavailable`, and `unknown`.

The table enforces allowlists, version 1, and numeric ranges. The RPC enforces event-specific required and forbidden fields, timestamp plausibility, and current catalog relationships.

Stage 5B must map the app's internal `custom` mode to `personalized`. Shared recommendation links use `shared_pick`. Search results currently reuse the common detail handler, so Stage 5B must pass `search` explicitly instead of allowing the current default context to classify them as personalized.

`recommendation_refresh` records the recommendation ID visible when the click occurs. A replacement set receives a new recommendation ID only after three valid cards are rendered. Web Share is recorded only after its promise resolves, clipboard sharing only after copying succeeds, and `AbortError` is never a success event.

Recommendation failures map only to `insufficient_candidates`, `invalid_result`, `data_unavailable`, or `unknown`; raw messages and stacks are never accepted.

## Timestamp Policy

`server_received_at` is generated by the database and is the Dashboard date source. Client `occurred_at` is accepted from 30 days before to 24 hours after the server statement time. This permits ordinary clock and retry variation while rejecting clearly implausible timestamps. Analytics failures remain separate from user-facing application behavior in Stage 5B.

## Catalog Policy

The table has no hard foreign keys to restaurants or menus, so future catalog cleanup cannot be blocked by Analytics history. The RPC verifies that referenced IDs exist and that a menu belongs to the supplied restaurant at ingestion time.

The RPC intentionally does not require `active=true` or `available=true`. A catalog row may change between display and the short non-blocking Analytics request; rejecting that legitimate display event would lose history.

## Recommendation Integrity

- `(recommendation_id, position)` is unique for shown events.
- `(recommendation_id, menu_id)` is unique for shown events.
- Two different menus from the same restaurant remain valid.
- A transaction advisory lock serializes shown rows for one recommendation ID.
- Existing rows for a recommendation must keep the same session and source context.

The advisory lock is necessary because three shown rows may be sent concurrently. It avoids a race where two first rows could otherwise establish different session or source values.

## Idempotency

The client supplies `event_id`; no server default is present. The RPC inserts with `ON CONFLICT DO NOTHING` and returns `true` for one new row or `false` for a primary-key or recommendation-uniqueness conflict. It never updates or deletes an Analytics row.

## Security

The ingestion RPC is `SECURITY DEFINER` with `search_path=pg_catalog` and schema-qualified application relations. `PUBLIC EXECUTE` is explicitly removed. Raw Analytics rows are unavailable to both ordinary users and administrator browsers. Stage 5D will add separate admin-only aggregate RPCs.

Anonymous submissions can be fabricated with developer tools, so these events represent product-usage trends rather than accounting, visits, sales, or verified real-world behavior. Rate limiting and anomaly detection remain future work.

## Rollback

Rollback is separately approval-gated and fails if the Analytics table contains any rows. It removes the exact ingestion function first and then the table without `CASCADE`. No existing public object is a rollback target.
